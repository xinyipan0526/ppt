# PPT Agent 项目全维度分析报告

> 审查方式：只读代码审查（未修改、新增或删除任何源码文件）。
> 结论均附源码行号证据；行号以审查时工作区为准，后续代码变动可能导致偏移。
> 文中所有文件路径均相对于仓库根目录（`E:\chatgpt_project\ppt`）。
> 覆盖维度：用户体验 / 生产级配置与运维 / 代码优雅度 / 结果产出与渲染导出 / Agent 循环控制 / 成本控制。

---

## 0. 总体判断（先给结论）

这是一份**后端工程水准显著高于前端、以"可靠性"见长的本地优先产品**。状态机、事务性持久化、崩溃恢复、成本账本、路径/HTTP 安全、打包发布这些硬骨头做得相当扎实，接近生产级；但**用户体验、可观测性、结果的自适应渲染、并发接线、全局预算上限**五处存在明确短板，且多处属于"后端已具备能力、前端没接上"的断层。

| 维度 | 一句话强项 | 一句话弱项 | 最重问题 |
|---|---|---|---|
| 用户体验 | 断线恢复/计费护栏扎实 | 前端明显滞后于后端能力 | 🔴 长任务无法取消 |
| 生产级配置运维 | 启动探测/恢复/安全严谨 | 可观测性与运维入口缺失 | 🔴 无日志、维护任务静默吞错 |
| 代码优雅度 | 领域契约/状态机一致性强 | 状态枚举与 Provider 复制债 | 🟡 状态用裸字符串、四处复制 |
| 结果产出/渲染 | 混合渲染+确定性排版+缓存身份好 | 核心自适应渲染缺失、零配置 | 🔴 `shrink_then_reflow` 未实现 |
| Agent 循环控制 | 状态机/恢复/幂等/SSE 投影质量高 | 并发未接线、无循环上界 | 🟡 Provider 限流/页面并发失效 |
| 成本控制 | 预留/结算/防重复计费严谨 | 缺全局硬顶、Provider 幂等缺失 | 🔴 总支出可达 4×预算 |

## 1. 用户体验

### 优点
- 断线兜底与恢复可视化扎实：SSE 断开/cursor 过期回退 3s 轮询（`web/src/api/events.ts`），后端游标续传 + retry 帧 + 有界批量（`src/ppt_agent/events/sse.py`）。
- 计费护栏到位：单页重生成前 `window.confirm`、全局重生成需勾选、对"结果未知"先引导去 Provider 控制台核对再授权重试（`web/src/features/deck/PageInspector.tsx`、`GlobalRegenerateDialog.tsx`、`web/src/features/runs/RecoveryActions.tsx`）。
- 澄清表单类型化（text/number/single_select/multi_select + reason + required，`web/src/features/planning/ClarificationForm.tsx`）。
- Provider 配置有 zod 校验与推荐模型预选（`web/src/features/settings/ProviderSetup.tsx`、`providerSchemas.ts`）。
- 单页历史一键恢复 + 四 Tab 详情；基础 aria-label / modal `role=dialog` / img alt / ≤900px 折叠（`web/src/app/App.tsx`、`web/src/styles/global.css`）。

### 缺点 / 风险
- 🔴 **长任务无法取消**：后端已有 `/runs/{run_id}/cancel`（`src/ppt_agent/api/production.py`），前端也订阅了 `run.cancelled`（`web/src/api/events.ts`），但全前端无任何取消按钮，等待长任务只能干等（`web/src/features/runs/RunStatus.tsx` 只展示进度）。
- 🔴 **模态可访问性不完整**：仅有 `role=dialog/aria-modal`，无焦点圈定、无 Esc 关闭、无焦点还原、无 `aria-labelledby`；全站无 `role=alert/aria-live`。
- 🟡 错误提示不一致：部分页面丢弃后端 `detail` 用泛化文案，部分展示 `ApiError.message`，项目创建失败甚至无错误态（`web/src/features/planning/PlanningInput.tsx`、`MaterialPanel.tsx` vs `ClarificationForm.tsx`、`ProviderSetup.tsx`）。
- 🟡 导出无进度、长请求阻塞（`web/src/features/exports/ExportPanel.tsx` 成功后直接下载，后端 `src/ppt_agent/api/production.py` 同步渲染）。
- 🟡 首次使用无 onboarding（新用户不知先配置模型）；AI 等待只有 step 徽标、无页级进度/ETA。

## 2. 生产级配置与运维

### 优点
- 配置分层 CLI>env>TOML>默认，`validate_settings` 校验 provider_mode/端口/并发/币种/价格与 cloud 必填（`src/ppt_agent/config/settings.py`）。
- Secret 处理严谨：0o600、临时文件 + `fsync` + `os.replace` 原子写、拒符号链接、脱敏与末 4 位掩码（`src/ppt_agent/config/provider_secrets.py`、`src/ppt_agent/api/security.py`）。
- 启动顺序清晰：探测→锁→迁移→完整性→对账→恢复→Supervisor→readiness（`src/ppt_agent/runtime/application.py`）；文件系统能力探测含 WAL 回退（`src/ppt_agent/storage/capabilities.py`）。
- 跨进程文件锁（`src/ppt_agent/storage/locking.py`）、Online Backup + manifest sha256 + 失败回滚（`src/ppt_agent/storage/maintenance.py`）、Host/Origin/CSRF/Bearer/Session + 资源级 `authorize_run` 双边界齐全（`src/ppt_agent/api/security.py`、`src/ppt_agent/runtime/composition.py`）。

### 缺点 / 风险
- 🔴 **可观测性缺失**：无日志配置、无结构化日志/指标；两个后台维护任务 `except Exception: pass` 静默吞错不落日志（`src/ppt_agent/runtime/maintenance.py`）。
- 🟡 备份/恢复无运维入口：CLI 只有 `serve/doctor/migrate`，无 `backup/restore` 命令、无定时备份，恢复需手工调库（`src/ppt_agent/cli.py`）。
- 🟡 无全局异常处理器，未映射 500 无结构化上下文；CLI 只捕获 `SettingsError/RuntimeError`，其余异常裸 traceback。
- 🟡 容器无 HEALTHCHECK、镜像未设 `PPT_AGENT_PRODUCTION`，直跑默认 `production=False`（`Dockerfile`、`src/ppt_agent/config/settings.py`）。

## 3. 代码优雅度与架构

### 优点
- 领域契约严格：`ContractModel` 用 `extra="forbid"` + 版本化 `SchemaEnvelope` + `model_validator` 交叉校验（`src/ppt_agent/domain/contracts.py`）；domain 层纯数据无副作用。
- 状态机纯函数化、与 spec02 表一一对应（`src/ppt_agent/domain/state_machine.py`）；状态与事件同事务 `UPDATE…RETURNING` 分配序号（`src/ppt_agent/events/persistence.py`）。
- 组合根清晰、依赖注入、反向所有权清理（`src/ppt_agent/runtime/application.py`）；Provider 统一能力抽象（`src/ppt_agent/providers/capabilities.py`、`registry.py`）。
- 测试分层合理：unit/integration/contract/live/e2e（`pyproject.toml`）。

### 缺点 / 风险（多为"代码异味"，属可维护性债而非功能缺陷）
- 🟡 Generation/Edit/Export 状态用**裸字符串**而非 `StrEnum`（`src/ppt_agent/workflows/production_store.py`、`deck_generations.py`、`page_editing.py`、`exporting.py`），与 Run/Step/Page 强类型状态机不一致。
- 🟡 四个 provider 复制同一套状态码映射与 usage 解析（`src/ppt_agent/providers/deepseek.py`/`ark.py`/`seedream.py`/`qwen.py`），应抽公共基类。
- 🟡 `StepEvent` 值大小写混合（"Completed" vs "step_started"），被迫用 `_event_identifier` 正则兜底（`src/ppt_agent/runtime/repository.py`），产生 `step.step_started` 与 `step.completed` 不一致。
- 🟡 状态机被绕过/字符串比较：`src/ppt_agent/workflows/planning_store.py` 直接赋 `SUCCEEDED` 不走 transition；`production_service.py` 用 `.value != "succeeded"`。
- 🟢 魔法数散落（1920×1080 多处重复、`"computed-by-text-runner"` 占位串、token 长度 43 vs 32 不一致）；`recovery.py` 把 session 声明为 `object` 连写 5 处 `type: ignore`；pyproject 无 ruff/mypy/black 配置。

## 4. 结果产出与渲染导出

### 优点
- 混合渲染落地：文字由结构化 PageSpec 编译为确定性文本块，HTML 模板只渲染 escaped 文本、不接受模型 HTML（`src/ppt_agent/rendering/layout.py`、`templates.py`）；先视觉资产后合文字（`src/ppt_agent/workflows/deck_production.py`）。
- 确定性排版 + 溢出检测：Chromium 固定 1920×1080/dsf=1、拦截网络、等字体加载，用 `scrollHeight>clientHeight` 逐元素上报实际字号（`src/ppt_agent/rendering/chromium.py`）。
- 缓存身份扎实（字体内容 sha256、图片请求指纹含 prompt/模型/尺寸/参考图哈希、manifest 指纹幂等落盘，`src/ppt_agent/rendering/fonts.py`、`providers/image.py`、`workflows/artifact_pipeline.py`）。
- 多层质量校验（像素级 + OCR 文案一致性 + 视觉"生成文字/入侵安全区"）；导出前复核页状态与质量、导出后复核 `pages_changed` 防 stale（`src/ppt_agent/workflows/exporting.py`）；PNG/JPG ZIP/PDF/PPTX 齐全；不可变代际恢复完整。

### 缺点 / 风险
- 🔴 **规格核心 `shrink_then_reflow` 未实现**：spec 要求"先缩字到 `min_font_size` 再重排"（`docs/specs/01-hybrid-rendering.md`），但模板固定字号 + `overflow:hidden`，溢出直接报 error 而非自适应；`min_font_size` 字段（`src/ppt_agent/domain/production.py`）渲染路径从不消费，只在样式编辑 clamp 用。**溢出即失败，而不是自适应**。
- 🔴 布局可配置性极低：layout 只产出 cover/title_body 两种 token，契约声明 6 种；坐标/字号/visual 框全硬编码（`src/ppt_agent/rendering/layout.py`）。
- 🟡 OCR 事后校验脆弱：用子串匹配 `normalize(expected) in normalize(ocr.full_text)`，OCR 漏字/错字会整页失败重试；确定性模式的 OCR 直接返回 expected_text，无法捕获真实渲染错误。
- 🟡 导出参数全部硬编码不可配（JPG quality=92、PDF resolution=144、纯栅格不可检索，`src/ppt_agent/exports/images.py`、`pdf.py`）；正文定位粒度粗，只能按 role/id 整体替换。

## 5. Agent 循环控制

### 优点
- 表驱动状态机 + 纯转换，非法转换抛 `InvalidTransition/GuardRejected`，写路径全走 `transition_*`（`src/ppt_agent/domain/state_machine.py`、`src/ppt_agent/runtime/repository.py`）。
- 状态变更与事件同事务、原子序号，回滚无空洞（`src/ppt_agent/events/persistence.py`）。
- Interrupt/Resume 版本校验 + 同 payload 幂等；崩溃恢复不自动重放（`RUNNING→recovery_required`、`submitted→reconciling`，`src/ppt_agent/runtime/recovery.py`）。
- Provider 两阶段提交 + 防重放（CAS `prepared→submitted`、非终态 Attempt 拒并发、未知结果需人工授权，`src/ppt_agent/operations/provider.py`）；SSE 纯投影（`src/ppt_agent/events/sse.py`）。

### 缺点 / 风险
- 🟡 **Provider 并发限未接线**：`provider_limits`/`provider_slot` 存在，但 composition 未传、无调用方，Semaphore 实际失效（`src/ppt_agent/runtime/supervisor.py` + `src/ppt_agent/runtime/composition.py`）。
- 🟡 **页面并发未实现**：`deck_production` 串行 `for page`，与 spec02 的 TaskGroup 边界（"A 失败 B/C 继续"）不符。
- 🟡 **循环无显式上界**：`while RUNNING` 无步数/代次/墙钟超时；revision 无限增 generation，每次 4 次 Provider 调用、仅单次预留（`src/ppt_agent/workflows/deck_planning.py`、`planning_store.py`）。
- 🟢 StepEvent 命名混用、取消对终态 Run 抛异常无幂等、一致读依赖 legacy BEGIN、ephemeral 修剪造成的 run_seq 空洞会误判 `cursor_expired`（`src/ppt_agent/events/store.py`）。

## 6. 成本控制

### 优点
- 原子预留正确：`BEGIN IMMEDIATE` 短事务内 `settled+active+held_unknown+amount≤hard_limit`，防并发超卖（`src/ppt_agent/ledger/costs.py`）。
- 结算四分类正确：成功 settle / 已知未计费 release（含 `confirmed_uncharged` 守卫）/ 已计费失败 settle / 未知 hold（`src/ppt_agent/operations/provider.py`）。
- `outcome_unknown` 不自动重发，仅人工 authorize-retry（`src/ppt_agent/api/operations.py`）；保守估算（文本 UTF-8 字节 +1.2 系数、视觉 1 字节=1 token）。
- 防重复结算：`usage_key/reservation_key` 唯一幂等，durable 结果重放免二次调用（`src/ppt_agent/operations/text_runner.py`）；UsageRecord 落 estimated/actual，预算 API 暴露 settled/active/held_unknown。

### 缺点 / 风险
- 🔴 **无全局项目硬顶**：四个 stage 账户各得全额预算，总支出可达 4×（`src/ppt_agent/api/projects.py` + `src/ppt_agent/runtime/backend.py` 各 stage 预留点）。
- 🟡 `idempotency_key` 仅本地持久化、未随请求发送，Provider 侧无幂等去重。
- 🟡 429/5xx 归 `outcome_unknown` 持有预算，`retryable + retry_at` 路径成死代码，限流需人工授权、预算长期占用。
- 🟡 图片预留按请求尺寸、结算按返回尺寸，上采样跨 2.61MP 阈值费用翻倍可超预留；`reasoning_tokens` 仅入 raw_units 不计价；价格表硬编码版本无自动校验（`src/ppt_agent/providers/catalog.py`）。

## 7. 跨维度共性问题（多个维度指向同一根因）

1. **"后端有能力、前端没接上"的断层**（用户体验 + 循环控制 + 成本）：取消、进度、预算展示、恢复授权后端都做了，前端只消费了一部分。这是当前"试用期体验差"的最直接原因。
2. **可观测性几乎为零**（运维 + 成本 + 循环）：无结构化日志/指标，维护任务静默吞错，导致成本异常、恢复失败、循环失控都难以被及时发现。
3. **硬编码与零配置**（结果产出 + 代码优雅 + 成本）：字号/布局 token/导出参数/价格表/并发度全部写死，无法按内容或预算调整"质量-成本"权衡。
4. **规格与实现存在落差**（结果产出 + 循环控制）：`shrink_then_reflow`、页面 TaskGroup 并发、Provider 限流都是"规格写了但没落地"，是当前最需要对齐的债。

## 8. 优先级改进路线（建议）

### P0（试用期体验与资金安全，先做）
1. 前端接上**取消按钮 + 页级进度/ETA**，统一错误展示（直接显示 `ApiError.message`）。
2. 补**全局预算硬顶**（跨 stage 汇总校验），并让 429 走安全重试释放预算，避免资金与预算长期被占用。
3. 加**结构化日志 + 全局异常处理器 + 维护任务失败告警**（把 `except Exception: pass` 全部落日志）。

### P1（结果质量与正确性）
4. 实现 `shrink_then_reflow`（缩字重排 + DOM 报告回传实际字号），补齐规格核心保障，让溢出从"失败"变为"自适应"。
5. 接线 Provider 限流 + 页面 TaskGroup 并发，并给 Run 增加显式代次/预算/墙钟超时上界。

### P2（工程质量与长期可维护性）
6. 引入 ruff + mypy，统一 Generation/Edit/Export 的 `StrEnum` 状态机，抽取 Provider 公共基类，收敛 SchemaEnvelope 解包与 artifact 提交为单一助手。
7. 补 `ppt-agent backup/restore` 命令、定时备份、容器 HEALTHCHECK(/ready)、镜像显式 `production=true`。
